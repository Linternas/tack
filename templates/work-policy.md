## Unified task and session records

- Use the globally installed `tack` CLI as the current-state source for tasks, decisions, dependencies, verification and resumption. Project documents remain detailed sources; reference rather than duplicate them.
- Simple questions and brief explanations need no task. Track code changes and analysis/reviews with follow-up work. At substantive task start run `tack status`, inspect a matching task with `tack task show ID` / `tack resume ID`, and reuse it instead of creating duplicates. `tack task add TITLE` automatically registers new projects.
- Record start, material state changes, interruption/handoff and completion. Small one-turn tasks need only a task and completion record; use checkpoints when resumption context is needed. Use the `handoff-state` skill for the CLI format.
- Existing task/session updates require the latest `version`. On conflict preserve input, read latest content and reconcile; never silently overwrite another writer.
- A session ending does not complete its task. Record task completion and session completion separately. Distinguish code checks, automated tests, browser checks and production verification; never claim unexecuted QA passed.
- Default storage is `~/.local/share/agent-work`, with one DB per project. Dashboard is optional: `tack dashboard`. CLI works without a server. `tack projects` lists global projects; `tack init --local` explicitly selects local storage for unregistered projects in restricted environments.
- Global storage also needs runtime sandbox write access to the data directory, including SQLite journal creation. File modes alone do not grant it. Config file changes do not retroactively change an active turn; supported host thread settings can update the same conversation for subsequent turns. Managed/app-injected permissions may override config. If the current roots exclude storage, use only the environment approval mechanism for the specific work command when authorized; never silently use another DB, Markdown or a server bypass. Verify task/checkpoint writes in the actual agent sandbox before claiming recording works.
- A write/permission failure must be reported and resolved within execution permissions. Do not silently create another DB, fall back to Markdown or claim an unsaved checkpoint succeeded. Do not broaden permissions solely to write an incidental work record.
- Do not create or maintain parallel work-plan, TODO, implementation-step, progress, QA-execution/result, review, completion or handoff documents, regardless of names such as plans/done/working/session or Markdown/HTML format. Store those in the same tack task/session DB, including planning-only requests. Ordinary planning, analysis or implementation does not authorize an extra dated file.
- Keep durable product requirements, business policy, API contracts, architecture/design and reusable technical instructions as source documents. If a document mixes these with work tracking, preserve the original in the DB and retain only source-of-truth content in the file. Native test/build artifacts remain tool-managed evidence, not another task ledger.
- Only an explicit request for a standalone document/file/report authorizes a separate deliverable; reuse the named artifact, and do not also create a session/completion note. Archived instructions/templates are historical evidence, not active workflow instructions.
- Do not create or update parallel `~/.codex/work-state/*.md` or repository session/handoff summaries. Existing files are historical sources, not active task indexes; consult only when directly relevant. Keep original records and backups unless deletion is explicitly authorized.
