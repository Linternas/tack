## Unified task and session records

- Use global `tack` for current work, decisions, dependencies, verification and resumption. Start substantive work with `tack search "relevant keywords"` (top 5 by default), then `tack resume TASK_ID` for the matching unfinished task. Search before creating a new task. Brief questions need no task. For cross-project results use the returned project ID with `tack --project PROJECT_ID ...`.
- The session performing or explicitly receiving a task owns its record lifecycle. Reuse the task for the same outcome, including tests, retries and reviews. Create a separate task only for an independently actionable outcome or blocker with its own completion condition. Bind the actual thread ID. Update only work you performed, verified or explicitly received. Cleanup is scoped to that work and its directly affected records.
- Group independently executable outcomes with `tack task add TITLE --parent PARENT_ID`. Use `tack task relations TASK_ID` to inspect hierarchy and incoming/outgoing links. Connect an established dependency, duplicate, replacement or reference with `tack task link TASK_ID TARGET_ID --type blocked_by|duplicate_of|superseded_by|relates_to --version VERSION`; remove an owned outgoing link with `task unlink`. Keep tests/retries/notes for the same outcome in its existing task. Relations describe structure; the performing session updates status from evidence. Complete a parent only after its open children and its own acceptance have been verified.
- Use the task's single `queue`: `todo`, `in_progress`, `issue`, `qa`, `waiting`, `done`, `archived`. Create with `tack task add TITLE --queue QUEUE` and change via versioned JSON containing `queue`. QA and unresolved problems stay in their own queue while being investigated or executed; use checkpoints for execution details. Move a problem to `todo` when its implementation scope is settled. Record the waiting condition in `next_action`. Task `category`/`status` are compatibility metadata; the default task interface uses `queue`.
- Mark actual API requests with `tack task add TITLE --api-request --queue waiting` or versioned JSON `is_api_request: true`. Use `tack status --api-only` to discover them. The API marker is independent of the task queue and is preserved when its work stage changes; clear it explicitly when the request scope changes.
- For UI-facing tasks, record the confirmed UI route in `page_path` using `tack task add TITLE --page /route` or versioned task JSON. Read the app router or verified browser location to identify the page. Exclude credentials and secret query values. Leave the field empty for non-UI work or an unverified route, and fill it when confirmed during owned work. This page locator is also shown in task summaries and agent-copy context.
- Before handoff or final response, reconcile owned task queue, verification, next action and resolved blockers using the latest version. Keep `in_progress` only while actual work continues. For unfinished work use `todo` with a next action, `waiting` with an unblock condition, or retain `issue`/`qa` for investigation and verification. Complete verified outcomes. Archive cancelled, superseded or duplicate tasks only with established scope/evidence and a reason or successor ID. Preserve history. Age, session exit and missing bindings alone never justify completion or archival. Leave other sessions' tasks intact and report unresolved ownership. Hand off the task ID, latest checkpoint and exact remaining action.
- Default `status`, `resume`, `task show` and `sessions` are bounded summaries. Use `tack status` for counts and a small recent index, `--search`, `--queue` or pagination for discovery. Read required acceptance, decisions and contracts before implementation. If `truncated_fields` is nonempty, or a long section is needed, use `tack record list TASK_ID --section SECTION`, then `tack record show RECORD_ID`; follow `next_record` or explicitly request `--full`. Use full task/history/session output only when needed. Avoid reading the same task through both resume and show.
- Keep current task fields concise: goal/scope, queue, blockers, next action and brief verification facts. Append substantial decisions, verification evidence and work notes using `tack record add TASK_ID --kind verification --text 'TEXT'` or `--file FILE`. Reference returned record IDs from brief task/QA fields. Record actual checks and failures; distinguish evidence from assumptions. Keep long chronological logs out of current task fields.
- Use `handoff-state` for checkpoints at meaningful handoff, pause, completion or expected context compression. Record new decisions, changed files, actual verification, blockers and next action concisely; reference existing records rather than repeating their bodies. Tack Core records work; optional orchestration is installed and explicitly invoked per project. Bind manually started development sessions with `tack bind THREAD_ID TASK_ID`; never guess ownership from the most recent task. Hook automation requires trust and actual event receipt.
- Preserve latest-version checks and reconcile conflicts. Record task completion separately from session/execution termination. Completion requires actual scoped verification. Keep work plans, progress, QA and handoffs in Tack. Durable product/API/design documents remain repository sources. Only explicit standalone deliverables authorize another report/file.
- CLI recording works without a server. Preserve the existing `~/.local/share/agent-work` database and project identities. On permission/write failure report unsaved state and resolve within approved permissions. Preserve failed input for retry. Avoid alternate work databases and server-based permission workarounds. Keep secrets and full conversations out of records. Remote Git writes, deployment, destructive actions and external messages require existing explicit authorization.
